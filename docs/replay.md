# Реплеи, метаданные и Game Coordinator

## Ключ реплея

Ссылку на реплей нельзя собрать без `replay_salt`, а его **не отдаёт Web API**.
Единственный источник — Game Coordinator, запрос `CMsgGCMatchDetailsRequest`,
для которого нужен Steam-аккаунт, залогиненный в Dota 2.

Лимиты, которые стоит уважать (они указаны прямо в коде OpenDota,
`svc/retriever.ts`): около **100 запросов матчей на аккаунт в сутки и 500 на IP**.
Поэтому поверх провайдера стоит суточный бюджет — по умолчанию 80 заявок,
счётчик в таблице `gc_budget`, команда `/budget` показывает остаток.

Важное свойство: запрос работает **по любому match_id**, а не только по матчам
самого аккаунта. Одного бот-аккаунта хватает на всех пользователей бота — так же
устроены OpenDota, Dotabuff и Stratz.

Сейчас в коде есть интерфейс `gc.Provider` и две реализации: `Disabled`
(бот работает без разбора, сводка по итоговой таблице) и `Manual` — ключи,
введённые руками:

```bash
export DOTA_MANUAL_SALTS="8999344582:181:1408381858,9000000000:135:123456789"
```

Формат — `матч:кластер:ключ`. Ключ виден в адресе реплея, который отдаёт
клиент Dota кнопкой «Скачать реплей».

## Метаданные вместо полного реплея

Рядом с реплеем по тому же адресу лежит файл метаданных:

```
http://replay181.valve.net/570/8999344582_1408381858.meta.bz2   70 КБ
http://replay181.valve.net/570/8999344582_1408381858.dem.bz2    43 МБ
```

Разница в шестьсот раз, а внутри метаданных уже есть многое из того, ради чего
обычно парсят реплей:

- порядок прокачки способностей;
- **снимки инвентаря каждые 30 секунд с таймкодами** — тайминги предметов даром;
- время получения каждого уровня;
- секунды контроля.

Чего в метаданных нет: координат вардов, треков героев, рун. Это только в полном
реплее.

Отсюда двухуровневый разбор: метаданные тянем всегда, следом качаем полный
`.dem` и разбираем его сами.

### Свой разбор .dem

`internal/replay` разбирает реплей библиотекой `dotabuff/manta` и считает:

- обзорные варды и сентри: кто поставил, когда, где, когда исчез;
- снятые чужие варды;
- поминутные кривые золота, опыта, добиваний и отказов;
- смерти с координатами.

Проверено сверкой с OpenDota на матче 8999344582: совпали счётчики вардов у
всех десяти игроков, снятые варды, добивания и золото к 10:00, число смертей.
Разбор занимает около двух секунд против ожидания в чужой очереди.

Три вещи, на которых пришлось повозиться, — они же ловушки для следующего раза:

**Классы сущностей пишутся непоследовательно.** Winter_Wyvern с подчёркиванием,
ShadowShaman без. Сопоставлять с именем героя из таблицы можно только после
удаления всех разделителей.

**У обзорного варда нет ссылки на владельца.** Ни при создании, ни позже —
в отличие от сентри, где она заполнена сразу. Владелец определяется по записи
боевого лога о применении вардового предмета в тот же момент, а если её нет —
по ближайшему союзному герою.

**События до гудка нельзя выбрасывать.** Момент нуля распознаётся по спавну
первой баунти-руны, то есть уже после нескольких вардов. Поэтому всё пишется в
тиках и переводится в секунды в конце разбора.

Чего здесь пока нет: стаки лагерей и участие в файтах. Стаков нет в боевом логе
этого патча вообще — перебраны все типы записей, события NEUTRAL_CAMP_STACK не
встречается ни разу. Их придётся считать слежением за лагерями нейтралов.

### Ловушка со сжатием

Оба файла приходят с расширением `.bz2`, но внутри давно **zstd**. `bunzip2`
молча не срабатывает и отдаёт исходные байты. Определяем по сигнатуре:

| Байты | Формат |
|---|---|
| `28 B5 2F FD` | zstd |
| `42 5A 68` (`BZh`) | bzip2 |

Реализовано в `meta.Decompress`, проверено тестом на настоящем файле.

### Разметка полей

Официальные описания лежат в `SteamDatabase/Protobufs`
(`dota_match_metadata.proto`). Текущий декодер читает нужные поля напрямую по
номерам — их разметка восстановлена по реальному файлу матча 8999344582:

```
CDOTAMatchMetadataFile { 1 version, 2 match_id, 3 metadata, 5 подпись }
CDOTAMatchMetadata     { 1 repeated Team }
Team                   { 1 team_id, 2 repeated Player }
Player                 { 2 repeated ability_id, 3 player_slot,
                         22 repeated level_up_time, 24 repeated Snapshot,
                         45 stuns (float) }
Snapshot               { 1 repeated item_id, 2 time }
```

Разметка проверена тестами, а не на глаз: секунды контроля Мираны совпали с тем,
что показывает OpenDota (70.7336), порядок прокачки — с её `ability_upgrades_arr`
у всех игроков, тайминг ботинок попал в ожидаемое окно.

## Почему нет изменения рейтинга

Проверено тремя способами, и везде пусто:

1. **Web API** — в `GetMatchDetails` таких полей нет.
2. **Реплей** — поиск по `AssignedRole`, `SelectedRole`, `Mmr`, `Rank` даёт
   только `m_bWasMVPLastGame` (флаг MVP **предыдущей** игры, приходит в матч уже
   готовым) и `m_unMmrBoost` — флаг матчмейкинга, не дельта.
3. **Файл метаданных** — четыре поля: версия, `match_id`, сами метаданные и блоб
   на 52 КБ, который **не разбирается как protobuf**, то есть зашифрован.
   Известные из OpenDota ранги игроков этого матча (34, 41, 53) не встречаются
   ни в одном поле.

Вывод: дельту рейтинга Valve в открытом виде не публикует. Медали игроков
(`rank_tier`) при этом доступны — их отдаёт Game Coordinator вместе с ключом
реплея.

## Свой скорборд

Итоги матча считаются по реплею, а не берутся из чужого разбора. Это не
украшение: матч 9002249594 попал в базу до того, как OpenDota его разобрала, и
остался бы без стаков, нейтралов, участия в файтах и без линий навсегда —
сохранённый скорборд больше не перечитывается.

### Где что лежит

| Сущность | Что даёт |
|---|---|
| `CDOTA_DataRadiant` / `CDOTA_DataDire`, `m_vecDataTeam.NNNN` | добивания, денаи, нетворс, заработанное золото и опыт, урон по героям и строениям, контроль, **стаки**, руны, варды поставленные и снятые, свитки, смоуки, вышки, Рошан |
| `CDOTA_PlayerResource`, `m_vecPlayerTeamData.NNNN` | убийства, смерти, помощь, уровень, **участие в файтах** |
| `CDOTA_PlayerResource`, `m_vecPlayerData.NNNN` | ник, медаль на момент матча |

Две ловушки в нумерации:

- `m_vecDataTeam` и `m_vecPlayerTeamData` нумеруются по игровому слоту, а
  `m_vecPlayerData` — по порядку подключения, и между записями попадаются
  наблюдатели. Привязка идёт по `m_iPlayerSteamID`, а не по индексу.
- Значения снимаются не на каждом обновлении сущности, а раз в две секунды
  игрового времени: сущность обновляется по многу раз в секунду, а важно только
  последнее значение.

**Стаки в боевом логе искать бесполезно** — события `NEUTRAL_CAMP_STACK` в нём
нет вовсе, это проверено перебором всех типов записей. Зато есть поле
`m_iCampsStacked`, и оно совпадает со счётом OpenDota точно.

### Сверка

```bash
n-dota-stats --verify 9002249594          # скачает реплей через GC
n-dota-stats --verify 9002249594 --dem путь.dem
```

Команда кладёт рядом наше значение и значение OpenDota по каждому игроку и
каждой метрике. На трёх проверенных матчах из 18 величин сходятся 17 — точно, по
всем десяти игрокам:

```
  убийства             сходится по всем 10 игрокам
  добивания            сходится по всем 10 игрокам
  нетворс              сходится по всем 10 игрокам
  урон по героям       сходится по всем 10 игрокам
  контроль             сходится по всем 10 игрокам
  стаки                сходится по всем 10 игрокам
  участие в файтах     сходится по всем 10 игрокам
  золото в минуту      сходится по всем 10 игрокам
```

Медаль намеренно не сверяется: в реплее лежит ранг на момент матча, а OpenDota
отдаёт текущий ранг из профиля — это разные величины, и расхождение между ними
ничего не говорит о качестве разбора.

### Чего воспроизвести не удалось: лечение

`hero_healing` в счёте Valve не получается ни из сущности, ни из боевого лога.

Поле `m_fHealing` считает что-то другое. Замеры:

| Герой | `m_fHealing` | Valve |
|---|---|---|
| Meepo | 33 798 | 0 |
| Juggernaut | 0 | 5039 |
| Spirit Breaker | 125 | 1670 |

По боевому логу пробовались три определения — всё подряд, только героям, только
союзным героям без себя. Ни одно не сошлось: в лог попадает регенерация и
вампиризм, и значения выходят на порядок выше.

Поэтому лечение остаётся единственной величиной из скорборда. Своё считается
отдельно и называется честно: `HealAllies` — вылечено союзным героям, без
самолечения. Для оценки саппорта это и осмысленнее.

Ещё одно расхождение, замеченное на одном игроке из тридцати: контроль у Tinker
2 секунды против нуля у OpenDota. Контроль они считают своим парсером, а не
берут у Valve, так что здесь расходятся две оценки, а не наша с эталонной.

## Линия, нейтралы и выкупы

Три величины, которых нет ни в сущностях со счётом, ни в скорборде Valve, —
раньше они приходили от OpenDota, теперь считаются сами.

**Выкупы** — записи `DOTA_COMBATLOG_BUYBACK`. Игрок лежит в поле `value`, это
его номер от нуля до девяти, а не слот. Сходится точно.

**Нейтралы** — записи `DOTA_COMBATLOG_DEATH`, у которых цель начинается с
`npc_dota_neutral_`, а атакующий — герой. Сходится у девяти игроков из десяти;
известное расхождение описано ниже.

**Линия** — голосование по позициям героя с 0:30 до 10:00. Точка относится к
линии по тому, с какой стороны от главной диагонали карты она лежит и насколько
далеко: полоса шириной 0,14 карты вокруг диагонали — центр, ниже — нижняя линия,
выше — верхняя. Первые полминуты пропускаются: все стоят на фонтане, а фонтаны
лежат на той же диагонали, что и центр.

Роль линии выводится из линии и стороны: нижняя линия лёгкая для Radiant и
сложная для Dire. **Совпало 10 из 10.**

## Ловушка с именами героев

Герои сопоставлялись со слотами по имени, и это молча не работало для тех, у
кого внутреннее имя другое: Io зовётся `Wisp`, Treant Protector — `Treant`,
Necrophos — `necrolyte`, Windranger — `windrunner`, и так примерно у четверти
списка. У таких героев терялись варды, смерти, нейтралы и линия — при этом
итоговый счёт сходился, потому что он читается по индексу, а не по имени.
Ошибку видно только на тех величинах, что идут через имя, и нашлась она именно
сверкой.

Теперь слот берётся из самой сущности: `m_iPlayerID` хранится удвоенным — у
первого игрока 0, у второго 2 и так далее до 18 (тип `uint32`, не `int32`).
Имя из боевого лога тоже больше не угадывается: раз слот известен, имя класса
сущности переводится в вид `npc_dota_hero_spirit_breaker` и запоминается. Таблица
имён строится из самого реплея, а не из догадок о том, как Valve зовёт героя.

## Открытое расхождение: нейтралы у Io

В матче 9002249594 у нас 135 убитых нейтралов, у OpenDota 161. Проверено
перебором всех целей, убитых Io: записей с префиксом `npc_dota_neutral_` ровно
135, юнитов с именем, содержащим `wisp`, в логе нет. Откуда у OpenDota
остальные 26, выяснить не удалось. У остальных девяти игроков значение сходится
точно.


## GetMatchDetails у Valve не работает

Проверено 17.09.2026: `GetMatchDetails` отдаёт HTTP 500 и пустое тело `{}` на
любом матче — и на свежем, и на матче 2014 года. Ключ при этом рабочий: без
ключа тот же запрос отвечает 403, а `GetMatchHistory` с этим же ключом работает.
Значит, дело не в нас.

Рабочий путь один — `GetMatchHistoryBySequenceNum`. Он отдаёт тот же полный
скорборд (включая `hero_healing`, которое мы не умеем считать сами), но по
сквозному номеру матча, а не по его id.

Сквозной номер приходит вместе со списком матчей игрока в `GetMatchHistory`,
поэтому связка такая:

```
GetMatchHistory        -> id матча + сквозной номер   (номер сохраняется в базу)
GetMatchHistoryBySeq   -> полный скорборд по номеру
```

Номер хранится в таблице `match_seq` отдельно от матча: он известен раньше, чем
сам матч загружен. Для матчей, которых мы не видели в списке игрока, номер
взять неоткуда, и для них источником остаётся OpenDota — это и делает
`app.Fallback`.


## Можно ли обойтись без Game Coordinator

Нет. Реплей лежит по адресу вида
`http://replayNNN.valve.net/570/<матч>_<ключ>.dem.bz2`, и без ключа его не
скачать. Проверено 17.09.2026: `GetMatchHistoryBySequenceNum` отдаёт `cluster`,
но `replay_salt` в ответе нет вовсе — полный список полей матча там такой:

```
barracks_status_*, cluster, dire_score, duration, engine, first_blood_time,
flags, game_mode, human_players, leagueid, lobby_type, match_id, match_seq_num,
picks_bans, pre_game_duration, radiant_score, radiant_win, start_time,
tower_status_*
```

Ключ отдаёт только Game Coordinator. Зато его нужно спросить **один раз на
матч за всё время**: ключ постоянный. Поэтому очередь такая:

1. **Ключ из базы.** Сохранённый ключ используется повторно — перечитывание
   истории новым парсером больше не стоит ни одного обращения к GC.
2. **Ключ из ответа OpenDota.** Он приходит в поле `replay_salt` вместе с
   матчем и тоже сохраняется. Если матч уже скачан, GC не нужен.
3. **Game Coordinator** — только когда ключа нет ни там, ни там.

Бюджет (80 обращений в сутки при валвовской сотне на аккаунт) теперь
списывается **до** запроса к GC. Раньше он списывался после — то есть ограничивал
скачивание реплея, а не то, ради чего заведён.

Ошибка, которая это вскрыла: колонка `matches.replay_salt` существовала, но
никогда не заполнялась. Два перезапуска разбора за день съели весь суточный
лимит на матчах, ключи которых уже лежали в базе в виде JSON.


## Применения предметов и способностей, попадания по героям

Раньше это приходило только из разбора OpenDota — отсюда и показатели
«Использовано TP», «Стрелы», «Крюки». Теперь считается по боевому логу:

| Что | Откуда |
|---|---|
| применения предметов | `DOTA_COMBATLOG_ITEM`, ключ без приставки `item_` |
| применения способностей | `DOTA_COMBATLOG_ABILITY` |
| попадания по героям | `DOTA_COMBATLOG_DAMAGE`, где и цель, и источник — герои |

Ключи приведены к тому же виду, что у OpenDota: предметы без `item_`, урон без
источника (обычная атака) записан как `null`. Иначе одни и те же величины
лежали бы под разными именами и сверить их было бы нечем.

Иллюзии отсеиваются по флагам `IsTargetIllusion` и `IsAttackerIllusion`: имя у
иллюзии то же, что у героя, так что одной проверки имени мало.

Сходимость: **применения предметов сходятся точно** (TP и смоуки — по всем
десяти игрокам), способности и попадания — **124 из 128**. Остаток разобран
ниже.

## Алтари мудрости и лотосы

`m_iWisdomShrinesTaken` и `m_iLotusesTaken` в той же командной сущности, что и
стаки. Сверить не с чем: OpenDota этих величин не публикует — это первые
показатели, которых у неё просто нет.


## Подчинённые и призванные юниты: считать по источнику, а не по атакующему

Игрок с доминатором, Чен, Чародейка, медведь Урсы, волки Ликана, паучата
Бродмазер — во всех этих случаях бьёт не герой, а его юнит. В боевом логе
атакующим записан юнит, и привязка по имени атакующего теряет всё, что он
сделал. У игрока с доминатором так терялась шестая часть добитых нейтралов:
135 вместо 161.

Имя юнита для привязки не годится: `npc_dota_neutral_polar_furbolg_ursa_warrior`
одинаково у подчинённого крипа и у любого дикого.

Решение оказалось в самом логе: **`damage_source_name`**. Valve записывает туда
хозяина — для героя это он сам, для его юнита это герой. Поле заполнено во всех
записях об уроне и смертях: проверено на реплее целиком, 32 500 записей, ни
одной без источника; отличается от атакующего в 417 из них.

```
команда 2 · npc_dota_neutral_polar_furbolg_ursa_warrior · источник npc_dota_hero_wisp  14
команда 2 · npc_dota_neutral_satyr_hellcaller          · источник npc_dota_hero_wisp   9
```

Поэтому убитые нейтралы, снятые варды и попадания по героям привязываются к
`damage_source_name`. Что это дало на матче 9002249594:

| | по атакующему | по источнику | у OpenDota |
|---|---|---|---|
| нейтралы у Io | 135 | 165 | 161 |
| способности и попадания, всего | 124 из 128 | **127 из 128** | — |

Способности подчинённых крипов и их обычные атаки теперь сходятся точно.

### Две несимметричные тонкости

Обе найдены перебором записей, а не выведены из общих соображений.

**Иллюзии.** Правило несимметрично: удар ПО иллюзии попаданием по герою не
считается, а урон ОТ своей иллюзии — считается, потому что иллюзия бьёт
по-настоящему и это вклад игрока. Так же считает OpenDota. Если фильтровать обе
стороны, теряются четыре попадания у игрока с Manta; если не фильтровать ни
одной, появляется лишнее попадание по чужой иллюзии.

**Свой подчинённый крип.** Он носит имя нейтрала, но переходит в команду
хозяина. Добить своего же подчинённого — не фарм леса, и такие смерти не
считаются; а вот чужого подчинённого считать надо. Поэтому сравниваются команды
цели и убийцы, а не просто проверяется, что цель нейтральная. На этом
расходились четыре убийства из тридцати.

### Что получилось

Проверено на трёх матчах: применения способностей и попадания по героям
сходятся **полностью** — 128 из 128, 125 из 125, 105 из 105. Линия — 10 из 10
в каждом. Нейтралы сходятся точно в двух матчах из трёх, в третьем расходятся
на одно убийство у Lifestealer.

Остаются известные расхождения: лечение (счёт Valve воспроизвести не удалось)
и контроль у Tinker в одном матче на 2 секунды.

## Что берём у Valve, а что считаем сами

Опыт у Meepo заставил провести границу явно. У него `m_iTotalEarnedXP` даёт
64 448 при 69 592 по таблице Valve — клоны собирают опыт мимо счётчика
основного юнита. У остальных девяти игроков того же матча наш пересчёт сходился
с таблицей до округления:

```
слот       наш XP      их XP   наш xpm   их xpm
0           41282      41248       733      732
4 (Meepo)   64448      69592      1144     1235
128         47532      47503       844      843
```

Отсюда правило: **числа, которые Valve публикует сама, берутся у неё, а не
пересчитываются**. Это убийства, смерти, помощь, уровень, добивания, денаи,
нетворс, золото и опыт в минуту, урон по героям и строениям. Свой разбор их
по-прежнему считает — ими проверяется правильность через `--verify`, — но в
сводку идёт значение из таблицы. Если таблицы нет вовсе, подставляется своё.

Свой разбор незаменим там, где таблица молчит: линия, стаки, варды, контроль,
руны, нейтралы, выкупы, участие в файтах, поминутные кривые, применения
предметов и способностей, попадания по героям, алтари и лотосы.


## Координаты смертей, путь героев и подборы

### Координат в боевом логе нет

Поля `location_x` и `location_y` в записи о смерти не заполнены вовсе — не нули,
а отсутствуют. Раньше мы читали именно их, поэтому все смерти оказывались в
точке (0, 0).

Зато есть `event_location` — грубая зона: 1 нижняя, 2 центр, 3 верхняя. Сама по
себе она мало что даёт, но служит бесплатной проверкой: координаты мы берём из
сущностей, а зону сравниваем с тем, что прислал Valve. На матче 9003682980
сошлись все смерти до единой.

Настоящая позиция берётся из последней известной точки героя: она обновляется в
том же потоке, что и боевой лог, и на момент смерти отстаёт не больше чем на тик.

### Путь героя

Позиция каждого героя пишется раз в пять секунд от гудка — примерно длина
одного рывка. Координаты умножены на четыре и округлены: карта в наших единицах
занимает 128 на 128, так что четверть единицы это около тридцати игровых.
Пропуск остаётся нулём, а не повтором прошлой точки: ноль честно означает
«героя не видели».

Разбор матча вырос с 31 КБ до 79 КБ — на 200 матчей это лишние 10 МБ.

### Когда забрали руну, алтарь, лотос

Событий подбора в боевом логе тоже нет: записей `PICKUP_RUNE` в реплее **ноль**,
ровно как и `NEUTRAL_CAMP_STACK`. Поэтому момент берётся по приросту счётчиков
`m_iRunePickups`, `m_iWisdomShrinesTaken`, `m_iLotusesTaken`, которые мы и так
снимаем раз в две секунды. Точность — те же две секунды.

Тип руны счётчик не знает, поэтому он приходит с другой стороны: когда сущность
руны исчезает с карты, запоминаем её тип, а потом привязываем к ближайшему по
времени приросту счётчика.

Проверка, что типы читаются правильно: водяные руны существуют только на второй
и четвёртой минуте, и обе руны этого типа у мидера оказались в 2:12 и 4:12.

Счётчики и подборы сходятся по всем десяти игрокам во всех трёх видах ресурсов —
это те же события, посчитанные двумя независимыми способами.


## Тепловая карта

Рисуется поверх настоящей карты Dota — той самой картинки, которой пользуется
OpenDota. Выбрана она не случайно: карта нарисована в той же системе координат,
что и позиции в реплее, от 64 до 192 по обеим осям, поэтому точки ложатся на
неё без подгонки. Картинка лежит в репозитории и вшита в бинарник, чтобы бот
не зависел от чужого сайта.

Плотность считается не по клеткам, а размазыванием каждой точки пути по
окрестности радиусом около радиуса обзора героя: клеточная сетка на такой
мелкой карте выглядит лесенкой.

### Нормировка: почему не по максимуму

Сначала плотность делилась на пиковую, и карта выглядела так, будто человек
простоял всю игру в одной точке. Проверка данных показала, что дело не в них:
в самой посещаемой клетке набирается около **десятой доли времени**, половина
укладывается в дюжину клеток из сотни занятых. То есть положения вовсе не
размазаны — виновата была шкала.

Теперь за «полную» плотность берётся **девяносто седьмой перцентиль** занятых
пикселей, всё выше упирается в красный. Девяностый пробовали — карту заливало
целиком, и разница между «стоял» и «прошёл мимо» пропадала.

Два числа, подобранных глазами по настоящим матчам:

- **радиус размазывания 22 пикселя**. Меньше — пятна рвутся, больше — линия
  перестаёт отличаться от леса.
- **сжатие плотности 0.8** поверх нормировки. Маршрут виден, но не спорит по
  яркости с местом, где человек реально стоял.

### Что отмечено на карте

Крестами — свои смерти, кружками — убитые враги. Разные фигуры, а не разный
цвет: на пёстрой карте форма различается даже боковым зрением, а цвет спорит с
самой тепловой картой. Координата убийства берётся у убитого — место смерти
врага и есть место убийства.

Цвет идёт от синего к красному, прозрачность растёт вместе с ним: на редко
посещённых местах карта должна просвечивать, иначе непонятно, где находишься.

Готовая картинка — JPEG 640 на 640, около 95 КБ. Без потерь та же картинка
весит впятеро больше при той же различимости пятен.

Текста на картинке нет намеренно: стандартный шрифт Go не знает кириллицы, а
тащить шрифт ради подписи незачем — подпись уходит отдельным полем сообщения.


## Карта вместо сводки в том же месте переписки

Хотелось переключать сводку и карту в одном сообщении. Телеграм этого не
позволяет напрямую: текстовое сообщение в сообщение с картинкой не
превращается, вид задаётся при отправке и правкой не меняется.

Держать сводку подписью к картинке тоже не вышло — подпись ограничена 1024
символами, а сводка в них не помещается. Замер по 260 накопленным сводкам с
учётом разметки: медиана **973**, девяностый перцентиль **1030**, максимум
**1096**; за предел выходит каждая восьмая.

Третий способ — показать картинку предпросмотром ссылки прямо в текстовом
сообщении — требует, чтобы картинка лежала по общедоступному адресу. Машина
бота за NAT, веб-сервера нет.

Поэтому переключение сделано **заменой**: старое сообщение удаляется, новое
встаёт на его место. Новых постов не копится, в переписке всё время одно
сообщение. Ограничение у способа одно: свои сообщения бот может удалять только
двое суток, дальше вместо замены появится новое.

Кнопки несут с собой место просмотра — свою историю со страницей, админский
список с пользователем и карточкой или обычную сводку. Иначе после возврата
было бы некуда вернуться: телеграм присылает обратно только данные кнопки, а
запоминать их негде.
