# Методика

## Модель «лучшего игрока»

Dota после матча показывает трёх игроков: лучшего и двух кандидатов. Формула не
опубликована, в Web API её нет, в реплее лежит только унаследованный от
предыдущей игры флаг `m_bWasMVPLastGame` — то есть награду считает Game
Coordinator уже после матча.

Рабочая гипотеза: отбор идёт **по перцентилям относительно того же героя**, а не
по сырым числам.

Признаки модели (`internal/mvp`):

золото/мин, опыт/мин, убийства, помощь, добивания, урон по героям,
урон по строениям, смерти (инвертированы).

Оценка — взвешенное среднее перцентилей. Стартовые веса равные.

**Лечение исключено намеренно.** У большинства героев оно нулевое, и ноль
получает высокий перцентиль просто потому, что таких же нулей много: в матче
8999344582 Night Stalker с нулевым лечением оказывается в 92-м перцентиле.
Метрика помечена в коде как `benchmarks.Degenerate`.

### Проверка

Матч 8999344582, экран Dota показал: **Winter Wyvern → Sniper → Naga Siren**.

Модель на равных весах даёт ровно тот же порядок:

| | Герой | Оценка |
|---|---|---|
| 1 | Winter Wyvern | 71.9 |
| 2 | Sniper | 64.4 |
| 3 | Naga Siren | 57.3 |

По сырым числам первой была бы Naga Siren: 28 846 нетворса, 771 GPM, 21 906
урона по строениям. Но для Naga Siren это 81-й перцентиль — хорошая игра, каких
на ней много, — а 483 GPM и 734 XPM для Winter Wyvern это 97-й и 89-й.
Нормировка по герою переворачивает картину и объясняет, как саппорт забирает MVP.

Одно совпадение — это наблюдение, а не доказанная формула. Дальше веса
уточняются на разметке пользователя.

### Обучение весов

`/fit` обучает условный логит: внутри матча игроки конкурируют за одно место
MVP, вероятность выбрать игрока — softmax от взвешенной суммы его перцентилей,
максимизируется лог-правдоподобие реального ответа. Градиентный подъём с
L2-регуляризацией, реализация в `internal/mvp/mvp.go`.

`/stats` показывает главное — точность обученных весов **против равных**. Пока
обученные не лучше равных, данных мало. Осмысленный порог — 15–20 размеченных
матчей, надёжный — от 40. Размечать промахи полезнее, чем попадания.

## Перцентили

OpenDota публикует кривую «значение на перцентиле» (p10…p99) по каждому герою и
метрике. Нам нужно обратное: по значению игрока найти его перцентиль. Делаем
линейной интерполяцией внутри кривой; ниже первой точки достраиваем отрезок от
нуля, потому что все метрики неотрицательны.

Снимок обновляется дважды в сутки — около 126 запросов за проход при лимите
2000, с запасом даже без ключа. Падение OpenDota не ломает бота: работает
предыдущий снимок.

Проверка: `TestPercentileMatchesOpenDota` сверяет наш пересчёт с готовым `pct`,
который OpenDota кладёт в матч. Расхождение держится в пределах шести пунктов —
кривые на их стороне обновляются, поэтому точного совпадения и не ждём.

## Lane efficiency

Формула зашита в OpenDota и **одинакова для всех ролей**:

```
melee    = 40 * 60 = 2400   // 60 ближних крипов
ranged   = 45 * 20 =  900   // 20 дальнобойных
siege    = 74 *  2 =  148   // 2 осадных
passive  = 600 * 1.5 = 900  // пассивный доход за 10 минут
starting = 600              // стартовое золото
знаменатель = 4948

lane_efficiency = золото на 10:00 / 4948
```

Это **не эффективность фарма**: в числитель идёт всё золото, включая убийства,
ассисты, баунти-руны и вышки. Пятёрка физически не может набрать много, потому
что крипов забирает керри. Поэтому сравнивать эту цифру можно только внутри
роли — что бот и делает.

## Медианы по ролям

Посчитаны запросами к `/api/explorer` OpenDota по последним 6000 разобранным
матчам на группу, сентябрь 2026. Роли в их данных нет, есть только линия,
поэтому группы выделены по поведению:

| Группа | Условие |
|---|---|
| керри | `lane_role = 1 AND obs_placed <= 2 AND last_hits > 120` |
| мид | `lane_role = 2 AND obs_placed <= 2` |
| оффлейн | `lane_role = 3 AND obs_placed <= 2` |
| саппорт | `obs_placed >= 5` (роум и хард вместе — разделить их в данных нечем) |

Шаблон запроса (без `LIMIT` упирается в таймаут):

```sql
WITH s AS (
  SELECT gold_per_min g, xp_per_min x, tower_damage td, camps_stacked cs,
         obs_placed op, lh_t[11] lh10, xp_t[11] xp10, gold_t[11] g10
  FROM player_matches
  WHERE <условие группы> AND gold_t IS NOT NULL
  ORDER BY match_id DESC LIMIT 6000
)
SELECT count(*) n,
 round(percentile_cont(0.5) within group (order by g))    gpm,
 round(percentile_cont(0.5) within group (order by x))    xpm,
 round(percentile_cont(0.5) within group (order by lh10)) lh10,
 round(percentile_cont(0.5) within group (order by xp10)) xp10,
 round(percentile_cont(0.5) within group (order by g10))  g10,
 round(percentile_cont(0.5) within group (order by td))   tower,
 round(percentile_cont(0.5) within group (order by cs))   stacks,
 round(percentile_cont(0.5) within group (order by op))   obs
FROM s
```

Результат (он же вшит в `internal/analysis/medians.go`):

| Группа | GPM | XPM | LH@10 | XP@10 | золото@10 | lane eff | вышки | стаки | варды |
|---|---|---|---|---|---|---|---|---|---|
| керри | 683 | 814 | 64 | 3629 | 3999 | 81% | 4504 | 2 | 0 |
| мид | 588 | 763 | 59 | 4578 | 3998 | 81% | 1048 | 1 | 2 |
| оффлейн | 534 | 663 | 51 | — | 3527 | 71% | 690 | 1 | — |
| саппорт | 330 | 475 | 7 | 2125 | 1840 | 37% | 120 | 2 | 9 |

**Важная поправка.** Если не отсекать саппортов по вардам, медиана «оффлейна»
падает с 71% до 55% lane efficiency: в выборку попадают пятёрки, стоящие на той
же линии. Первая версия этих цифр была посчитана без фильтра и занижала планку
для коров.

Обновлять таблицу стоит раз в патч — запросы те же.

## Откуда берётся каждый показатель

| Источник | Что даёт |
|---|---|
| Steam Web API `GetMatchDetails` | итоговая таблица: KDA, GPM, XPM, добивания, урон, предметы, уровень |
| Файл метаданных матча | прокачка, тайминги предметов, время уровней, секунды контроля |
| Полный реплей `.dem` | варды с координатами, треки героев, руны (пока не реализовано) |
| OpenDota `/benchmarks` | кривые перцентилей по героям |
| OpenDota `/explorer` | медианы по ролям (разово, вшиты в код) |

Показатель объявляется одной записью в `analysis.Registry` и сам сообщает, какой
уровень данных ему нужен, — до появления этих данных строка просто не
показывается.
